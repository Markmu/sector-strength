## 范围说明

本用例文档只覆盖 **plan-03 管理端分组管理页面**（FEAT: plan-03）：

### 需要新增的 mock / fixture

新增 helper 文件 `web/tests/e2e/helpers/mock-shareholder-api.ts`（参照 `mock-fund-api.ts` 模式）：

- `createTestShareholderGroups()` — 工厂：返回 5 个预定义组（与 plan-01 种子数据一致：国家队/外资投行/社保基金/保险公司/私募基金），字段 camelCase（id/name/description/isSystem/ruleCount/matchedStockCount/keywords）
- `mockShareholderGroupsList(page, groups)` — Mock GET `/api/v1/admin/shareholder-groups`，按调用序号可返回不同结果（支持"删除后刷新列表"场景）—— 实现时用计数器或可切换 fixture
- `mockShareholderGroupsListError(page)` — Mock GET 返回 500
- `mockShareholderGroupCreate(page)` — Mock POST 返回成功（新建 id=100）
- `mockShareholderGroupCreateConflict(page)` — Mock POST 返回 400「组名已存在」
- `mockShareholderGroupUpdate(page)` — Mock PATCH `/api/v1/admin/shareholder-groups/{id}` 成功
- `mockShareholderGroupDelete(page)` — Mock DELETE 成功
- `mockShareholderGroupPreview(page, matchedCount)` — Mock GET `/api/v1/admin/shareholder-groups/preview` 返回 `{ matchedStockCount }`

> 注意：plan-01 的 Admin API response 是否包 `{ success: true, data: ... }` 外层，需在写 spec 时核对实际后端实现（参照 `test_shareholder_group_admin_api.py` green 证据中的字段命名）。本 red 阶段先按本仓库 admin mock 通用模式（admin-fund-sync 用 `{ success, data }`）写，若 green 阶段发现 response 外层不同再调整——不影响 red 阶段"功能未实现 → 测试失败"的结论。

### 选择器稳定性自检（遵循规则 5/7）

- 所有断言优先使用 `getByRole('button'/'dialog'/'heading')` + `name` 精确/正则匹配，不依赖易变文案做唯一等待条件
- 多处出现的文本（如「QFII」可能同时出现在表格行和 dialog）一律用 `main` 区域或 `dialog` 容器限定（`page.locator('main')` / `page.getByRole('dialog')`）
- 按钮文案采用正则模糊匹配（如 `/^保存$/`、`/^新增分组$/`）以应对文案微调
