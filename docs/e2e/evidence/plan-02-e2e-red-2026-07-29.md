# plan-02 E2E Red 证据：ETF 历史回填（14 期）

## 结论

**预期失败，测试有效。**

- plan-02「历史回填」是纯后端 task handler 功能（无 UI），BACKFILL_ETF_HISTORY 任务是 etf_daily 历史段数据写入的唯一执行者。按 auto-dev / test-e2e skill 规则，task handler 功能不允许 E2E 豁免，本功能的 red 验证形态为 **pytest 集成测试（执行验证）**，非 Playwright（参照 plan-01 先例 + MEMORY「后端 FEAT E2E 适配 pytest」）。
- 新增 **11 个测试用例全部失败**，失败原因均为「目标功能尚未实现」：
  - 4 个用例 → `TaskType 未定义 BACKFILL_ETF_HISTORY` / handler 未注册到 TaskRegistry / `backfill_etf_history_task 未加入 __all__`（任务类型与 handler 未注册）
  - 1 个用例 → `EtfDataInitService 缺方法 backfill_etf_history`（回填 service 方法不存在）
  - 2 个用例 → `api/admin 未导出 init_etf_history_router` / `cannot import name 'init_etf_history'`（admin 历史回填端点未注册）
  - 4 个执行验证用例 → 因 `TaskType.BACKFILL_ETF_HISTORY` / `backfill_etf_history` 方法不存在，无法走到"触发任务 → 查库"的断言路径
- 测试文件可被 pytest 正常收集（**11 tests collected in 1.27s**），无 ImportError、无语法错误、无 collection error——失败完全来自被测功能缺失，符合 red 关键原则。
- 现有 `tests/test_etf_daily_sync.py`（plan-01）**10 个用例全部通过**（无回归破坏），证明本期新增测试改动未破坏既有功能。

## 时钟解耦（吸取 plan-01 red 测试教训）

plan-01 的 red 测试曾把"今天"硬编码为绝对日期导致跨午夜失败（collector 按规格用 `datetime.now(BJ_TZ).date()` 取当日采集）。plan-02 天然无此风险——**backfill 接受显式 `start_date`/`end_date` 参数**（不从系统墙钟取日期），因此测试设计为：

- `BACKFILL_START = date(2026, 7, 20)`、`BACKFILL_END = date(2026, 7, 24)` 固定日期（5 个工作日），作为 backfill 的入参，**与系统墙钟完全无关**。
- mock 数据的 `trade_date` 与 `start/end` 对齐（`_fake_fund_share` 按 `BACKFILL_TRADING_DAYS` 的日序号生成确定性递增份额）。
- mock 交易日历 `get_trading_calendar()` 只返回这 5 天，保证 backfill 的 `TradingCalendar.get_trading_days_between()` 筛选结果确定。
- 断言查的也是这些固定日期，任意系统墙钟下结论一致。

这样测试既验证了"曲线无断裂 / share_change 依赖上一日"的核心语义，又彻底避免了时钟耦合。

## 数据源 mock 策略

执行验证用例通过 `unittest.mock.patch("src.services.data_acquisition.DataSourceFactory.create")` 注入确定性 mock 客户端（`get_fund_basic_etf` / `get_fund_share` / `get_fund_nav` / `get_trading_calendar`），使任务执行链路不依赖外部 Tushare（当前 token 全局过期）。这与 task handler 的"数据写入唯一执行者"契约无关——task handler 的核心职责是按日期升序逐日复用 sync_etf_daily 把数据写入 etf_daily 并保证 share_change 依赖上一日，数据从哪来（mock 或真实 Tushare）不影响写入与计算逻辑的验证。

mock 数据刻意构造覆盖 §5 曲线无断裂验证的确定性断言：
- 三只宽基 ETF（510300.SH / 512100.SH / 159915.SZ），与 plan-01 测试同口径便于 cross-check。
- 每只 ETF 每日份额 = 基线 + 日序号 × 步长，保证升序逐日回填时 share_change = 固定步长（510300 步长 50000、512100 步长 10000、159915 步长 5000）。
- unit_nav 固定（510300=4.0、512100=2.5、159915=3.0），net_inflow = share_change × unit_nav / 10000 可精确断言（如 510300 第二日 net_inflow = 50000×4.0/10000 = 20.0）。
- 交易日历只含回填范围 5 天，保证 TradingCalendar 筛选确定。

## 未放宽的核心业务断言（实现后须全部精确成立）

- 任务流转：`create_task` → `start_task` → handler → `complete_task(success=True)` → `status == "completed"`。
- 回填范围 5 个交易日每个都有 etf_daily 记录，每交易日记录数精确 == 3（3 只宽基 ETF）。
- share / unit_nav 非空（逐条断言）。
- 首日（2026-07-20）share_change / net_inflow 为 null（ADR-3 预期，非断裂，逐条断言）。
- 第二日 share_change = 当日 − 前日：510300 == `Decimal("50000.0")`、512100 == `Decimal("10000.0")`；net_inflow：510300 == `Decimal("20.0000")`、512100 == `Decimal("2.5000")`。
- 全范围逐日 share_change = 当日 − 前日（曲线连续无断裂，覆盖 ADR-5 同口径复用）。
- task.total == 5、task.progress == 5（逐日推进）；有 AsyncTaskLog 记录（可观测性）。
- service 直调返回 `{total_days: 5, processed_days: 5, failed_days: 0}`。
- admin init_etf_history_router 暴露 POST /init/etf-history 端点。
- 构建前置：`EtfDataInitService.backfill_etf_history`、`TaskType.BACKFILL_ETF_HISTORY`（value='backfill_etf_history'）、handler 注册且 callable、`backfill_etf_history_task` 在 `__all__`、`api/admin.init_etf_history_router`——逐条精确断言。
