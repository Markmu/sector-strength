### 本次相对 red 阶段的唯一改动：修正测试设计的时钟耦合（非放宽断言）

red spec 把"今天"硬编码为 `TRADE_DATE = date(2026, 7, 29)` / `PREV_TRADE_DATE = date(2026, 7, 28)`，而 collector 按规格用 `datetime.now(BJ_TZ)` 取当日采集（`server/src/services/data_updater/collector.py` `_update_etf_daily`：`today = datetime.now(BJ_TZ).date()` → `trade_date = today.strftime("%Y%m%d")`）。spec 编写时刻系统墙钟在 07-29，但执行验证时已跨午夜到 07-30，collector 实际写入 `trade_date=20260730`，测试却仍查 `2026-07-29`，导致 KeyError（查不到数据）。

主 agent 日志已证实实现完全正确：采集成功写入 3 条、share_change=50000、net_inflow 公式、幂等覆盖、宽基归类 broad 全对（freezegun 冻到 07-29 时 10/10 通过）。**根因是测试设计缺陷，非实现缺陷。**

本次改动**只解耦时钟、不放宽断言**，让测试在任意系统墙钟下都断言"collector 实际取的那个当日"，而非耦合到固定绝对日期：

1. `TRADE_DATE` 改为 `datetime.now(ZoneInfo("Asia/Shanghai")).date()`，与 collector 实际取日逻辑完全一致。
2. `PREV_TRADE_DATE = TRADE_DATE - timedelta(days=1)`，保持"前一日"相对关系。
3. mock `_fake_fund_nav_factory` 的 `nav_date` 由硬编码 `"2026-07-29"` 改为 `TRADE_DATE.strftime("%Y-%m-%d")`，确保服务内 `_dates_equal(nav_date, trade_date)` 在任意日期都命中（`trade_date` 由 collector 以 `today.strftime("%Y%m%d")` 传入，`_dates_equal` 归一化去 `-` 后比较）。

### 未放宽的核心业务断言（全部保持精确值）

- 任务流转：`create_task` → `start_task` → handler → `complete_task(success=True)` → `status == "completed"`。
- etf_daily 当日记录数精确 == 3（不是 >0）。
- share / unit_nav 非空（逐条断言）。
- 首日 share_change / net_inflow 为 null（架构 §6.1 实现原则，逐条断言）。
- **share_change = 当日 − 前日**：510300 == `Decimal("50000.0")`、512100 == `Decimal("-10000.0")`。
- **net_inflow = share_change × unit_nav / 10000**：510300 == `Decimal("20.0000")`（50000×4.0/10000）、512100 == `Decimal("-2.5000")`（−10000×2.5/10000）。
- 幂等：预置旧值 share=999999.0，重复采集后记录数仍 == 3（on_conflict 覆盖），510300 share 覆盖为 `Decimal("1200000.0")`。
- 归类：etf_basic 记录数 == 3；宽基 510300/512100/159915 的 `category` 全 == `"broad"`；index_name 非空。
- 构建前置：EtfBasic/EtfDaily 可导入且在 `models.__all__`、`TaskType.SYNC_ETF_DAILY` 定义且 value='sync_etf_daily'、handler 注册到 TaskRegistry 且 callable、`sync_etf_daily_task` 在 `task_handlers.__all__`、`EtfDataInitService.sync_etf_daily/sync_etf_basic` 可导入、`DataCollector._update_etf_daily` 存在——逐条精确断言。
