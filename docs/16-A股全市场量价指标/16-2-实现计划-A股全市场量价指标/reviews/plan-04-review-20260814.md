## 4. 双 advisory lock key 设计裁定（要求 #5）

**裁定：拆分正确，实现符合架构意图，无互斥漏洞，无 key 冲突风险。**

### 4.1 架构意图对齐

架构 §4.3（line 148）明确区分两个锁目的：

> "事务级 lock 保证同类创建原子性，专属会话级 lock 只保证 `sync_market_metrics` 单 owner"

实现拆分为：
- `MARKET_METRICS_LOCK_KEY=9001001`：`create_exclusive_task` 内 `pg_advisory_xact_lock`（事务级，commit 即释放）—— 串行化并发同类**创建**。
- `MARKET_METRICS_OWNER_LOCK_KEY=9001002`：executor `pg_try_advisory_lock`（会话级长连接）—— 保证**单 owner**。

这与架构 §4.3 / §6.2.2 / §6.2.3 对创建锁（§6.2.2 "pg_advisory_xact_lock(key)"）与 owner 锁（§6.2.3 "独立长连接取得专属 session advisory lock"）的分别描述一致。

### 4.2 共用同一 key 的死锁风险（确认实现理由成立）

若两个锁共用同一 key：executor 持会话级 `pg_try_advisory_lock`（非事务、长连接、长期持有）期间，专用入口 `create_exclusive_task` 的 `pg_advisory_xact_lock` 是**阻塞式**的，会无限等待 executor 释放——而 executor 只有进程退出/连接断开才释放。这会让任务创建永久阻塞。因此**必须拆分为两个 key**。

### 4.3 "running 含停止中/待 recovery 占用互斥" 语义是否充分

owner 持 9001002 期间，创建走 9001001，互斥决策完全由 DB 查询保证：

```python
# create_exclusive_task 内：
pg_advisory_xact_lock(9001001)   # 串行化并发创建的 check-then-insert 临界区
SELECT id WHERE task_type='sync_market_metrics' AND status IN ('pending','running')
# 命中 → 返回 None（拒绝）
```

充分性分析：
- 停止中任务（已写 `cancel_requested_at`/`timeout_requested_at`）仍为 `status='running'`，直到 `finalize_*_with_result` 原子提交终态——被查询命中，占用互斥。符合架构 §8.3"running 含停止中/待 recovery 均占用，确认退出或新 owner 回收后才释放"。
- 待 recovery 的 stale running 同为 `status='running'`——被查询命中。
- `pg_advisory_xact_lock(9001001)` 仅串行化"查存在→插入"的 TOCTOU 竞态（两并发创建都看到无存在任务），不承担"长期占用"语义——后者由 DB 行的 status 承担。这是正确的职责分离。

**结论：DB 查询 + 事务级创建锁的组合充分保证互斥，无漏洞。**

### 4.4 两个 key 取值冲突风险

- `pg_advisory_xact_lock(bigint)` 与 `pg_try_advisory_lock(bigint)` 均用单 bigint 形式（PostgreSQL 单 key 与 (int,int) 双 key 是不同锁空间；此处全用单 key）。
- 9001001 ≠ 9001002，分属不同 advisory lock 对象，无冲突。
- 全仓 grep 确认这两个 key 常量仅在 task_manager（9001001 唯一使用点）与 task_executor（9001002 唯一使用点）出现，无其他地方误用。

## 8. 建议项（非阻塞）

1. **recovery 提交前未复验 acquisition 有效性**：架构 §6.2.3 提到"事务提交前再次验证当前 acquisition 未失效"。`TaskManager.recover_stale_market_metrics_tasks` / `_recover_one_stale` 在 TaskManager 层无法访问 guard，未在 commit 前复验 acquisition token/guard 有效性。实际风险低：recovery 写入的是基于持久化字段的确定性终态，且 `SELECT FOR UPDATE` 行锁已串行化 recovery 与在途事务；recovery 在 `_on_mm_owner_acquired` 内同步执行（持锁后立即跑、guard 激活前）。guard 复验主要服务于 handler 的 fence 业务写事务（§6.2.6），该路径已在 `lock_and_validate` 实现。建议 plan-05 handler 落地时确认该语义在端到端执行验证中无副作用。

2. **`_recover_one_stale` 终态保留原 token**：recovery 终态后任务行 `executor_acquisition_token` 仍为旧/NULL token（未清空）。这不影响正确性（终态任务不再参与互斥/ fencing），但 `test_acquisition_recovers_stale_running` 已断言此行为。建议保持现状，记录于 plan-05 交接。
