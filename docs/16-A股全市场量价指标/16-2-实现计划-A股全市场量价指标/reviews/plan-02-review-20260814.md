### 专项裁定 #3：页签名守卫——签名 =（首行 key + 行数），offset 不参与身份判定

**裁定：偏离可接受，满足架构 §6.1.3/§6.1.6「页签名重复→失败」的意图。**

- 架构原文（§6.1.3 / §3.2 / §8.6）只要求「维护页签名……签名重复……失败」，**从未规定 offset 参与签名身份**；「（首行 ts_code + 行数 + offset 的元组）」是 plan-02 §3 的转写。而 offset 由引擎自身严格递增（每满页 +3000），若纳入身份元组则任意两页签名必不相同，「签名重复」守卫成为永不可达的死代码——plan 文本自相矛盾，实现是对规格笔误的修正而非偏离意图。
- 威胁模型吻合：该守卫针对「代理忽略 offset 重复回页」（§8.6「异常重复满页」）。同一内容页在不同 offset 上重现时，(首行 key, 行数) 必然重合 → 守卫可达且有效（`test_page_signature_repeat_raises` 正是此场景）。offset 仍记入错误信息供排查。
- 误报分析：两页恰同首行 key 且同行数但内容不同 → 判重复报错。但同 key 重现本身即意味着行 key 跨页重复（单日 key=ts_code、历史 key=(ts_code,trade_date)），本就是完整性违规——守卫 fail-safe（宁可误杀不放过），方向正确。
- 纵深防御仍在：即便签名守卫因内容变形漏检，「跨页重复行 key」「满页无新增 key」「页数超硬上限」三层守卫独立兜底，架构「不静默截断、不死循环」的底线不受影响。
- 历史模式 key 含 trade_date：一股在窗口内合法多日行，若 key 仅 ts_code 会误报完整性错误——复合 key 是正确设计（有专门用例验证跨页复合 key 重复拦截）。

### 专项裁定 #4：suspend_d 上游缺陷处理契约

**裁定：契约足以支撑 AC-13（架构 §6.1.5 当日停牌确认），且已充分记录。**

- **信息完备性**：架构 §6.1.5 需要的输入是「目标日 T 的停牌记录（suspend_type + suspend_timing）」。适配器保真返回上游全量行且逐行携带归一化 `suspend_date`，plan-03 客户端过滤 `suspend_date==T` 后即得到完整的当日停牌证据——`suspend_type='S'` 判定与 `suspend_timing` 全天规则所需字段无一丢失。真实冒烟验证：全量 5000 行 → 过滤后 4 条当日记录，且 5539+4=5543 恰好闭合 L 集合，原料侧集合平衡可复现。
- **被迫性**：上游代理忽略 `suspend_date` 查询过滤（任意日期返回同一批跨 301 个日期的全量行）且日期列名为 `trade_date`（官方为 `suspend_date`，显式请求该字段只得全空列）——服务端过滤在此代理下不可实现，客户端过滤是唯一可行方案。适配器仍传 `suspend_date` 查询参数，官方接口语义下（若换回官方端点）即恢复服务端过滤，双键归一化保证两种 schema 均兼容。
- **成本**：每次调用仍为 1 次 suspend_d 请求（架构 §8.1「1 次 suspend/日」预算不变），仅多传输约 5000 行（≈2 页 daily 体量），可接受。
- **失败安全网**：若上游行被截断丢失当日记录，plan-03 按 §6.1.5「无法判定者失败」+ §6.1.7 集合平衡（daily+全天停牌==expected）会**响亮失败**而非静默错数据——数据损坏风险被下游守卫封死。
- **记录充分性**：已在 plan-02 §5（实现规格 #5）、§交接上下文（「suspend_d 上游行为补充（实现级）」）、`base.py` 抽象方法 docstring、`tushare_client.py` 实现 docstring、`SuspensionRecord` 模型 docstring 共 5 处显式声明「plan-03 必须客户端过滤 `suspend_date==T`」——plan-03 消费方不可能漏看。

**结论**: 实现规格全部满足；两处自报偏离均裁定为正确决策。通过。
