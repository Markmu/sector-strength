### 维度 9：代码审查 — 通过（无 blocker，有 2 个建议项）

**正确性审查**（重点核对公式 / 幂等 / 归类 / null 语义）：

- net_inflow = `share_change × unit_nav / 10000`（亿元）正确，与 510300=20.0 / 512100=−2.5 的断言一致。
- 幂等：on_conflict_do_update(constraint='uq_etf_daily_date_code', set_ 5 字段) 正确，重复执行同日覆盖旧值。
- 归类：宽基整串相等比较（`extracted == idx_name`）天然规避"沪深300自由现金流"误归；长名优先排列；行业关键词 + other 兜底不抛异常。
- 首日 null：prev_share is None → share_change/net_inflow = None 正确。
- 前日份额子查询 `trade_date < target ORDER BY trade_date DESC LIMIT 1` 正确。

**安全审查**：Tushare token 仅服务端持有（tushare_client 从环境变量读，不暴露前端），采集频率日级 + 0.3s 限流避免风控 — 符合架构 §8.3。

**无数据损坏风险**：upsert 均在事务内 commit；单只失败 catch 不影响整批。

**建议项（非阻塞）**：

1. `collector._update_etf_daily` 返回 `processed`（实际为 upsert 处理数），handler 日志措辞为 "rows upserted" — 措辞与返回值语义可更明确（upsert 无法精确区分 insert/update），但不影响功能正确性。
2. sync_etf_daily 的 `added`/`updated` 计数：upsert 模式下 added 统计为所有成功处理数、updated 固定为 0 — 这是 PG on_conflict 的固有限制（仿 _update_sector_fund_flow 范式），已在 docstring 说明，可接受。


| 检查点 | 结果 |
| --- | --- |
