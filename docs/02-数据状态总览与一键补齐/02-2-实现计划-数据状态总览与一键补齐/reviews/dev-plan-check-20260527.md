## 六、问题清单

| 严重级别 | 位置 | 问题 | 修补建议 |
| --- | --- | --- | --- |
| 🔴 blocker | plan-02 §3 step 3 | 路由前缀 `prefix="/admin/data"` 错误。admin 路由已在 `router.py` 以 `prefix="/v1/admin"` 挂载，再叠加 `/admin/data` 会变成 `/api/v1/admin/admin/data/...`，与架构 §7.3 定义的 `/api/v1/admin/data/status` 不符。经验证：`init.py` 用 `prefix="/init"`、`tasks.py` 用 `prefix="/tasks"` | 改为 `prefix="/data"` |
| 🔴 blocker | plan-03 §5 | E2E-TDD 验收项（"打开数据管理页面验证数据状态标签页"）未关联 `docs/e2e/` 下的具体测试用例或目标 Playwright spec，也未明确 red/green 两阶段证据留存方式。`docs/e2e/` 目录当前不存在 | 在 plan-03 Task 列表中新增 Task（或在现有 Task 中明确）：创建 `docs/e2e/02-e2e-用例-数据状态标签页.md` 测试用例文件，覆盖三张卡片状态展示、补齐按钮点击、进度轮询、失败重试等核心路径；验收标准中的 E2E-TDD 行指向该文件 |
| ⚠️ 建议 | plan-03 §3 step 1 & 3 | 轮询实现使用 `useEffect` + `setInterval` + `mutate()` 自定义方案，偏离架构 ADR-4 和 §4.2 推荐的 SWR `refreshInterval: 2000`。功能等价但增加手动定时器管理负担（清理、卸载等） | 改为 SWR 条件式 refreshInterval：`refreshInterval: hasActiveTask ? 2000 : 0`，与 ADR-4 一致且代码更简洁。如确需自定义方案，在实现规格中说明偏离原因 |
| ⚠️ 建议 | plan-01 §3 step 2 | L1 降级策略（交易日历不可用时只返回 latest_date）仅在边界场景表中提及，实现规格中未说明触发条件（TradingCalendar 抛异常？超时？返回空？） | 在 get_status() 实现规格中补充降级触发逻辑：`try/except` 包裹 TradingCalendar 调用，异常时 status 设为 "normal"（无法判断缺失），missing_range 设为 null |
| ⚠️ 建议 | plan-03 §5 + 边界场景表 | 补齐按钮点击后的错误处理只覆盖了 409 冲突（边界场景表），验收标准只检查"API 调用成功后立即刷新状态"，未覆盖补齐 API 返回非 409 错误（网络超时、500 等）时的前端行为 | 在验收标准中补充：`补齐 API 调用失败（非 409）时显示错误 toast 或提示，按钮恢复可用`；在边界场景表中补充对应行 |
| ⚠️ 建议 | plan-02 §3 step 2 | backfill_ma handler 逐日循环逻辑未说明如何处理单个交易日失败（是否跳过继续？还是整体失败？）。大量缺失日期时逐日循环中途失败会导致部分数据已补齐部分未补齐 | 在实现规格中明确：单日失败时记录 WARNING 日志并继续下一日，最终汇总成功/失败天数作为进度报告；或在风险与边界中说明此场景的处理策略 |
