### 红线核查（implementer 在实现期修改 red spec 和 mock helper 的合理性）

| # | 修改项 | 类别 | 判断 |
| --- | --- | --- | --- |
| 1 | mock helper `route.continue()` → `route.fallback()`（mock-shareholder-api.ts） | 测试基建 bug 修正 | **合理**。多个 helper 在同 URL 注册时，Playwright LIFO 调用 handler，非本方法处理时必须 `fallback()` 转交下一个 handler；若用 `continue()` 会跳过其它 handler → ERR_CONNECTION_REFUSED。11/11 通过证明此修复是必须的。**与实现 bug 无关、不影响断言**。 |
| 2 | 删除行选择器歧义（spec TC-1.7/1.8/1.9）：`tr.filter({ hasText: 'QFII' })` → `table.getByText('QFII', { exact: true }).locator('xpath=ancestor::tr')` | 选择器歧义修正 | **合理**。mock 数据「外资投行」描述含子串「（QFII）」，与 QFII 组名共用「QFII」导致 strict mode violation（原选择器匹配 2 行）。修改后用精确文本 + xpath 唯一定位。**断言未放宽**（仍要求精确匹配 QFII 行 + 删除/取消按钮 + 列表消失/保留），反而增强了精确性。 |
| 3 | AlertDialog role 适配（spec TC-1.7/1.8/1.9）：`getByRole('dialog')` → `getByRole('alertdialog')` | 组件 role 匹配 | **合理**。plan-03 §3.2 明确要求用 shadcn AlertDialog，Radix AlertDialog 强制 `role="alertdialog"`。**这是测试侧 role 适配，不是断言放宽**。`toBeVisible()`、`getByRole('button', { name: /^取消$/ })`、`getByRole('button', { name: /^确认删除$/ })` 等关键断言完全没改。 |

**断言是否放宽的明确判断**：**没有任何断言放宽。**

逐一核查 spec 中可能被怀疑的"宽松"写法：

- **TC-1.5（L213-216）`toBeVisible().catch(async () => {...退化断言...})`**：先尝试 `getByRole('textbox', {name: /中央汇金/})`，失败回退到 `getByText('中央汇金', {exact:true}).first().toBeVisible()`。**回退仍是 visible 断言**，预填充校验未降级（关键词"中央汇金"必须可见）。
- **TC-1.6（L187-189）`/匹配到?\s*3\s*只股票|匹配\s*3\s*只/`**：主匹配仍是"匹配到 3 只股票"。用例文档 §TC-1.6 期望文案"当前规则匹配到 3 只股票"，spec 主分支完全对应。副匹配是兼容性兜底，**与用例文档一致**。
- **TC-1.10（L333-335）`/组名已存在|操作失败|保存失败|失败/`**：用例文档 §TC-1.10 明确允许"含「组名已存在」或「失败」关键词"，spec 完全照用例文档实现，**未放宽**。
- **TC-1.11（L345-347）`/加载失败|加载出错|请求失败|失败/`**：同 TC-1.10，用例文档 §TC-1.11 允许"加载失败"或 toast，spec 兼容多文案，**未放宽**。

整体核查结论：spec/mock 的所有修改都是**测试侧技术修正**（Playwright mock bug、选择器歧义、Radix 组件 role 匹配），没有任何**断言放宽、验收标准降低或关键断言删除**。TDD 红线未被突破。
