## 3. 关键护栏代码级核实

> 不只看测试通过，逐条读真实代码确认护栏落实。

### 3.1 持仓计入无阈值（ADR-2）

`fund_crowd_repository.py:75-107` 的聚合 SQL 仅含 `WHERE report_period = :p` + 可选 `scope` 过滤 + 可选 `search` 过滤，**无任何 `stk_mkv_ratio >= 1.0` 或 `stk_float_ratio` 阈值**。grep 确认 `stk_mkv_ratio` 仅出现在文件头注释，未进入 WHERE 子句。对比 04 `fund_repository.py:376` 的 reverse-lookup 硬编码 `stk_mkv_ratio >= 1.0`，plan-01 的「存在即重仓」口径与 ADR-2/ADR-4 边界完全一致。

### 3.2 NULL 处理：主动型 `.is_(None)` 显式包含

`fund_crowd_repository.py:86-94`：

```python
if scope == "active":
    stmt = stmt.where(
        or_(
            Fund.invest_type.notin_(passive_invest_types),
            Fund.invest_type.is_(None),
        )
    )
```

SQLAlchemy `or_(.notin_(...), .is_(None))` 生成 `invest_type NOT IN (...) OR invest_type IS NULL`，**不会因 `NOT IN` 漏掉 NULL 行**。测试 `test_rankings_returns_active_scope_only` 断言 `fundCount=2`（001001 主动 + 001004 NULL），若 `.is_(None)` 缺失会得到 1，测试会失败——证明护栏真实生效。

### 3.3 主排序 + 辅排序

`fund_crowd_analysis_service.py:150-152`：

```python
items.sort(key=lambda x: (-x["fund_count"], -(x["total_float_ratio"] or 0)))
```

- 主排序 `fund_count` 降序（COUNT DISTINCT fund_ts_code）
- 辅排序 `total_float_ratio` 降序（SUM stk_float_ratio）
- `or 0` 让 None 视为最小（L3 降级场景兼容）

测试 `test_rankings_order_by_fund_count_desc` 严格断言 `symbols.index("600519") < symbols.index("000001")`（600519 fundCount=4 > 000001 fundCount=2）。

> 注：排序在 Python 层而非 SQL `ORDER BY`（plan §3 #2.1 step 7 允许两种路径）。影响仅限跨页时同一 fund_count 的次序不稳定，但单期内扎堆股 fund_count 大量重复概率低，且前端按页加载，非阻塞。

### 3.4 is_new 三态 + hasPrevPeriod=false 全 null

`fund_crowd_analysis_service.py:186-193`（`_compute_changes`）：

```python
if not has_prev_period:
    for symbol in current_agg:
        changes[symbol] = {
            "fund_count_change": None,
            "total_float_ratio_change": None,
            "is_new": None,  # ADR-3：has_prev_period=false 时 is_new=null
        }
    return changes
```

显式生成 `is_new: None`（不是 False），与 ADR-3 三态契约一致。测试 `test_rankings_no_prev_period_returns_null_changes` 同时断言三字段全 None（`is None`，不接受 False）。

`is_new=True/False` 分支在 :195-213，新进 `fund_count_change=None`（非 0），符合 AC-03。

### 3.5 camelCase 响应 + snake_case query

- 路由层 `Query("active")` / `Query(None)` / `Query(1, ge=1)` / `Query(20, ge=1, le=100)` 全 snake_case（`fund_crowd_analysis.py:135-144`）
- `_dict_to_camel` 递归转 dict/list，`_serialize_value` 处理 Decimal/date（:104-129）
- 测试通过 `data["hasData"]` / `item["stockSymbol"]` / `item["fundCountChange"]` 等 camelCase 键直接访问响应，证明转换生效

### 3.6 search SQL 注入防护

- `_escape_like_keyword`（service:27-29）：转义 `\` → `\\`、`%` → `\%`、`_` → `\_`
- `.like(f"{escaped}%", escape="\\")` / `.ilike(f"%{escaped}%", escape="\\")`（repository:102-104）
- SQLAlchemy 参数绑定，无字符串拼接
- 测试 `test_rankings_search_escapes_like_wildcards` 断言 `search=%` 时 `total=0`（不匹配全表），证明转义生效

## 4. 代码审查：建议项（非阻塞）

### 建议项 1：`_dict_to_camel` / `_escape_like_keyword` / `_serialize_value` 重复定义

`fund_crowd_analysis.py:104-129` 的 `_dict_to_camel` 和 `_serialize_value` 与 `funds.py:106-124` 同名同实现重复；`_escape_like_keyword` 与 `shareholder_analysis_service.py:37`、`shareholder_group_service.py:87` 重复。

plan-01 §8 风险与边界「允许修改的额外文件」已明示「若 helper 已在某模块存在，可改为 import 复用而非重复定义」——agent 选择重复定义是 plan 允许的路径，非越界。建议后续 plan（或运维阶段）抽到 `src/api/v1/_helpers.py` / `src/services/_like_helpers.py` 统一复用，降低维护成本。

### 建议项 2：排序在 Python 层而非 SQL 层

`get_rankings` 先在 SQL 层 GROUP BY（无 ORDER BY），再 Python 内存排序 + 切片分页。plan §3 #2.1 step 7 允许此路径，但生产环境 15 万行级别单期 ~1 万扎堆股全部 Python 排序存在轻微性能开销（架构 §8.1 目标 < 3s 仍可达，因 LIMIT 4 报告期 + WHERE report_period 过滤后单期数据量可控）。

非阻塞，建议未来若性能压测不达标，可改为 SQL `ORDER BY fund_count DESC, total_float_ratio DESC` + LIMIT/OFFSET。
