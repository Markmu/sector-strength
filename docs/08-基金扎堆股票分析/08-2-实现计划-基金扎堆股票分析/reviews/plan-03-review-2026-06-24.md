## 1. 抖动问题专项判定（★ 重点审查项）

### 1.1 事实复核（源码 + 证据交叉核对）

读了 `web/src/app/dashboard/funds/reverse-lookup/page.tsx` 全文，确认 `ReverseLookupContent` 内 `data-testid="back-to-fund-crowd"` 出现在 **3 个 return 分支**（line 192-209 `!symbol` / line 248-265 `isError` / line 292-309 主结果），`fund-crowd-drilldown-hint` 仅在主结果分支（line 312-319）。

**关键澄清（与 green 证据 §8 的措辞略有补充）**：3 个 return 分支是 **JSX 互斥**的（`if (!symbol) return ...` 早返回，`if (isError && !isLoading) return ...` 早返回，否则主 return）。**任何单次 React render 只会渲染其中 1 个分支**，3 个 testid 按钮从不会在「同一稳定 DOM」下并存。

green 证据 §8 的 DOM 探针实测（t≈0ms count=2，t≈100ms count=1）印证：瞬时双元素并非来自 3 分支并存，而是 **Next.js dev 模式 + `useSearchParams` Suspense 边界首帧双渲染产物**（React Strict Mode 双调用 / Suspense 恢复时双 mount）。生产 build 无 dev 双渲染，故不复现。

### 1.2 判定 1：是否违反 Playwright 规则 5？

**不违反规则 5 的设计意图**。

规则 5 原文针对的是「textarea 内容和预览标签都包含相同文本」这类**同一稳定 DOM 下结构性多匹配**——`getByText()` 解析到多个元素并抛 strict mode violation，根因是选择器写法不够精确，修复方向是 `.first()` / `filter` / 精确匹配。

本抖动是**dev 模式瞬时渲染产物**：同一选择器在收敛后（t≈100ms）解析到唯一元素，选择器本身（`getByTestId('back-to-fund-crowd')`）已经是规则 7 推荐的「稳定结构化标记」。规则 5 的 `.first()` 收敛建议在此场景**可缓解但不治本**——治本要靠消除 dev 双渲染（生产 build 即消除）。spec 侧选择器已遵循规则 5/7 的最佳实践。

### 1.3 判定 2：33% 偶发失败率是否可接受？

**可接受（针对当前 dev 模式本地 E2E）**。理由：

1. **生产 build 不复现**：green 证据 §8 已确认。CI 若用 `npm run build && next start`（生产模式）跑 E2E，抖动消失。本项目 `playwright.config.ts` 无 `webServer` 配置，dev server 由手动/CI 脚本启动——CI 侧切到生产 start 即彻底消除。
2. **功能本身正确**：6 轮中 4 轮稳定 5/5 通过，2 轮失败的根因是 Playwright strict mode 在首帧（t≈0ms）硬抛错且部分场景不触发自动重试收敛，与实现逻辑无关。
3. **AC-05 全部 5 个场景在稳定基线下通过**，TC-3.4 / TC-3.5（扎堆页侧）从未抖动（不经过 04 反查页的 Suspense + useSearchParams 渲染路径）。
4. **green 证据已明示「交 task-review 判断」**，符合 plan-03 §8 风险与边界对 dev 模式 timing 偏差的预警授权。

**但需提请注意**：若未来 CI 必须用 dev server 跑 E2E（例如受限于 build 资源），33% 失败率会显著拖累 CI 信号质量。因此给出**非阻塞收敛建议**（§1.4），由后续 FEAT 或维护任务承接。

### 1.4 判定 3：3 个 return 分支重复内联同一 testid 是否代码异味？

**轻度代码异味，非阻塞**。

- **非结构缺陷**：3 分支互斥，不会产生稳定的 DOM 重复（如判定 1 所述）。当前写法功能正确。
- **可维护性问题**：返回入口按钮的 JSX 在 3 处复制（`router.push('/dashboard/fund-crowd-analysis')` + `ArrowLeftIcon` + 文案 + className），未来改文案/样式需改 3 处，易漏。这是真实的代码异味。
- **与抖动的关联**：抽取共享组件**不能消除** dev 双渲染抖动（抖动来自 Suspense + useSearchParams，与组件内联与否无关）。green 证据 §8 建议 2「抽为命名组件降低双渲染窗口」表述偏乐观——抽组件主要收益是可维护性，对抖动收敛无实质帮助。

**最小修复建议（非阻塞，记录给后续维护）**：

1. **实现侧（推荐，治可维护性）**：抽取 `<BackButton fromFundCrowd={boolean} />` 共享组件，3 个 return 分支调用同一组件。消除 3 处 JSX 复制。
2. **spec 侧（治抖动表象，仅 dev 模式）**：TC-3.1/3.3 的 `toBeVisible()` / `click()` 改用 `.first()` 或 hint 用 `getByRole('note')`（hint 仅主结果分支有，天然唯一）。但这会**放宽**选择器精度，与规则 5 精神有张力，不作为强推荐。
3. **CI 侧（治本，治抖动）**：E2E 切生产 build 运行。

### 1.5 抖动最终判定

**可接受，verdict: pass**。不构成 blocker：
- 不违反规则 5 设计意图（选择器已是最优实践，抖动来自 dev 渲染产物）；
- 生产 build 不复现，功能正确；
- 已有零成本收敛路径（CI 生产 build + 实现侧抽组件）。

建议项（非阻塞，不回 implement）：实现侧抽 `<BackButton>` 共享组件消除 3 处 JSX 复制；CI E2E 切生产 build。
