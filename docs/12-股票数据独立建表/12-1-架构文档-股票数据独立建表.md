# 12-1 架构文档：股票数据独立建表

_本文件只保留当前版本真正影响实现的架构决策、边界和契约；DDL、目录树、环境变量、实施故事等内容默认不放入正文。_

## 1. 系统摘要

本需求将 A 股个股的行情、均线、强度三类时序数据从"与板块共用同一张表（靠 entity_type 区分）"拆出为三张股票独立表。板块继续使用原表，代码完全不动；股票读写路径整体切换到新表，旧股票数据留在原表不迁移、不读取，靠后续增量采集重新积累。

核心闭环锚点：**Collect → Write(new) → Read(new)**（采集 → 写新表 → 读新表）。

## 2. 范围、非目标与成功标准

### 2.1 范围

1. 新建三张股票独立表：`stock_daily_market_data`、`stock_moving_average_data`、`stock_strength_scores`，含字段、约束、索引
2. 股票数据写入路径整体切换到新表：行情采集、历史初始化、增量/按日补齐、均线计算、强度计算、级联删除
3. 股票数据读取路径整体切换到新表：MA 数据加载、强度查询、排名、强度历史、强度快照、API 直查、质检
4. 旧表（`daily_market_data` / `moving_average_data` / `strength_scores`）保留结构，仅承接板块数据；旧表中遗留的股票历史数据不删除、不读取

### 2.2 明确不做

- 旧股票历史数据搬移（接受重新采集积累，长周期指标如 240 日均线有自然空窗期）
- API 响应字段与前端界面的任何改动（保持 `entity_type` 响应字段、snake_case 命名、响应包裹结构）
- 缓存 key 命名调整（`strength:stock:{entity_id}:{date}` 等保持现状）
- 激活现有死代码 Repository 层（`MarketDataRepository` / `MovingAverageRepository` / `SymbolMarketDataRepository`）
- 为股票新增独立的强度/均线 task handler（保持现状：个股强度由 API 同步触发批量计算，个股均线无调度入口）
- 字段语义重新设计（个股死字段 `ma5_score` 等照搬，不在本期清理）

### 2.3 成功标准

| 指标 | 首版目标 |
|---|---|
| 数据隔离 | 新采集的股票数据全部落入新表，原表不再新增 entity_type='stock' 记录 |
| 个股功能延续 | 个股分析、个股排名、个股强度历史接口行为与改造前一致 |
| 板块功能零回归 | 板块相关全部功能行为完全不变 |
| 对外接口契约 | 个股相关接口响应字段名、类型、结构保持不变，前端无需改动 |

### 2.4 验收标准承接矩阵

| AC-ID | PRD 原文摘要 | 承接模块 | 关键链路 / 状态 | 风险 / 降级说明 |
|---|---|---|---|---|
| AC-01 | 股票数据彻底分开：新采集股票数据落入新存储，原存储不再新增个股记录 | collector 股票分支 + 新表模型 | 链路 L1（行情采集）→ 写 `stock_daily_market_data` | 风险：on_conflict 约束名需同步改为新表唯一约束，否则插入报错 |
| AC-02 | 个股读取动作切换：个股接口返回数据来源于新存储 | ma_data_loader / stock_ma_service / strength_service_v2 / stocks.py / rankings.py | 链路 L4（个股读）→ 全部指向新表 | 风险：ma_data_loader 同时服务 stock/sector，需按 entity_type 内部分发，不能误伤板块 |
| AC-03 | 板块功能零回归 | 全部板块 service + sectors.py | 板块链路完全不动，继续读旧表 | 风险：shared 工具方法（ranking_service / strength_history_service）改动时误改 sector 分支；对策：分支隔离 + 板块测试门禁 |
| AC-04 | 随个股删除清理数据 | data_init.\_cascade_delete_stock_data | 级联删除遍历新三表 | 风险：漏改某张表导致删除残留；对策：删除函数对 (StockDailyMarketData, StockMovingAverageData, StockStrengthScore) 三元组遍历。板块侧零改动，旧表板块数据天然不受影响 |
| AC-05 | 字段语义收敛 | 三张新表模型定义 | 新表去除 entity_type/period(强度表)/板块专属字段 | 风险：误删 `percentile`（运行时 setattr 的"幽灵字段"）；对策：见 ADR-3，新表必须保留 percentile 列 |
| AC-06 | 对外接口约定不变 | stocks.py / rankings.py / strength.py 个股分支 + api/schemas/strength.py | API 层读写切新表，响应 schema 不动 | 风险：响应里 `entity_type` 字段继续硬填 "stock"，前端零依赖（已确认） |
| AC-07 | 长周期指标空窗期呈现 | ma_data_loader / stock_ma_service | 新表无 ma240 数据时返回空 | 既是已知约束也是验收项：呈现"数据不足"，前端无需新增降级 |

## 3. 用户流程与状态

### 3.1 主流程

本需求无新用户交互流程，是后端数据存储层改造。可观察流程仅"数据维护者触发采集 → 数据落入新表 → 读路径返回新表数据"。

### 3.2 关键分支

| 分支名 | 入口 / 触发条件 | 架构处理方式 |
|---|---|---|
| 股票行情采集 | 调度器或手动触发 `init_historical_data_task` / `backfill_by_date_task` / `backfill_by_range_task` | collector 股票分支写 `stock_daily_market_data`，on_conflict 指向新表唯一约束 |
| 股票均线计算 | service 直调 `StockMAService.calculate_*` | 写 `stock_moving_average_data`（read-modify-write 模式照搬） |
| 股票强度计算 | API 触发 `StrengthServiceV2.calculate_stock_strength` 或 `batch_calculate(entity_type='stock')` | `_save_strength_score` 内部按 entity_type 分发到新表 |
| 个股级联删除 | `init_stocks` 清理已退市股票 | `_cascade_delete_stock_data` 遍历新三表 + SectorStock + Top10FloatHolder + Stock |
| 板块任意操作 | 任意板块接口/任务 | **完全不动**，继续读旧三表 |

### 3.3 状态机

无新增状态机。个股数据沿用了既有"采集 → 入库 → 计算 → 读取"的隐式状态流转，本次仅替换存储目标。

## 4. 系统上下文与模块职责

### 4.1 系统上下文

变更点（其余依赖关系不变）：

- 旧三表（`daily_market_data` / `moving_average_data` / `strength_scores`）今后只承接板块数据
- 新三表（`stock_daily_market_data` / `stock_moving_average_data` / `stock_strength_scores`）承接全部个股数据
- 数据源（DailyQuote / Tushare 等）、前端、API 契约、缓存层、调度器配置均不变

### 4.2 模块职责

| 模块 | 职责 | 上游输入 | 下游输出 | 改动说明 |
|---|---|---|---|---|
| 新表模型层 | 定义三张股票独立表的字段、约束、索引 | — | ORM 元数据 | 新建 3 个模型文件，去 entity_type，强度表去 period 与板块专属字段，保留 percentile（见 ADR-3） |
| collector 股票分支 | 股票日线行情采集入库 | Tushare DailyQuote | `stock_daily_market_data` | `pg_insert` 目标改为 StockDailyMarketData；on_conflict 约束名改为新表唯一约束；entity_type 字段不再赋值 |
| DataInitService 股票路径 | 股票历史初始化与级联删除 | Stock 列表 + DailyQuote | 新三表 + Stock/SectorStock/Top10FloatHolder | 写入读查重指向新表；`_cascade_delete_stock_data` 遍历新三表 |
| DataUpdateService 股票路径 | 股票按日/按区间补数据 | 目标日期 + Stock | `stock_daily_market_data` | entity_type='stock' 写入切新表 |
| StockMAService | 个股均线计算 | `stock_daily_market_data` | `stock_moving_average_data` | select/insert 全切新表；read-modify-write 模式照搬 |
| StrengthServiceV2 个股分支 | 个股强度计算与保存 | ma_data_loader + 行情 | `stock_strength_scores` | `_save_strength_score` 按 entity_type 内部分发模型类；`calculate_and_update_change_rate` 同步分发 |
| MADataLoader | 通用 MA/价格数据加载 | 行情表 + 均线表 | dict | 按 entity_type 分发到 stock/sector 模型（核心共享工具，最易误伤板块，需重点测试） |
| RankingService | 排名/百分位计算 | 强度表 | 强度表 rank/percentile 列 | `for entity_type in entity_types` 循环内按类型选模型 |
| StrengthHistoryService | 强度历史查询 | 强度表 | 序列化数据 | stock 分支切新表，sector 分支不动 |
| StrengthSnapshotService | 强度快照统计 | 强度表 | rank/percentile | stock/sector 两个分支分别选模型 |
| data_quality 个股分支 | 股票数据质检与异常补齐 | 行情表 + 强度表 | 报告 + 补数据 | 股票行情补齐与强度异常检测切新表 |
| API 股票端点 | 个股对外接口 | 强度表/均线表（直查） | 响应 schema | `stocks.py` / `rankings.py`(v2 stocks) / `strength.py`(stock 分支) 切新表；响应字段不变 |
| 板块全部模块 | 板块全部功能 | 旧三表 | — | **零改动**，作为回归基线 |

> **复用可行性验证**：本次"切换到新表"不引入新服务，所有改动都是把既有 service/repository 内"对 entity_type='stock' 的查询/写入"指向新模型类。验证要点：
> - collector 股票分支：现用 `pg_insert(DailyMarketData).values(entity_type='stock', entity_id=stock.id, ...)`（`collector.py:290-306`）→ 改为 `pg_insert(StockDailyMarketData).values(stock_id=stock.id, ...)`，约束名同步替换
> - ma_data_loader：现 `select(MovingAverageData).where(entity_type == entity_type, ...)`（`ma_data_loader.py:102-127`）→ 按 entity_type 选 MovingAverageData 或 StockMovingAverageData
> - ranking_service：现 `for entity_type in entity_types: select(StrengthScore).where(entity_type==..., ...)`（`ranking_service.py:61-97`）→ 循环内按类型选模型

### 4.3 需要刻意避免的过度设计

- **不引入股票独立 Repository 层**：现有 Repository（MarketDataRepository 等）本就是死代码，本次不借机激活，避免扩大改动面
- **不为股票新增 task handler**：现状下个股强度由 API 同步触发、个股均线无调度入口，本期维持现状，不为对称性新增 TaskType 常量与 handler
- **不做字段语义重新设计**：个股死字段（`ma5_score` 等）虽然实际无写入，但照搬避免破坏 schema 完整性；语义清理是后续独立工作
- **不引入数据同步/双写层**：旧表与新表不并行写入、不做透明代理，明确"一刀切"切换降低复杂度
- **不为空窗期引入补偿逻辑**：长周期指标缺失按既有"数据不足"方式呈现，前端无新降级

## 5. 关键架构决策（ADR）

### ADR-1：物理拆表而非软隔离

- **选择**：新建三张物理独立的股票表，板块继续用原表
- **理由**：共用表靠 `(entity_type, entity_id)` 软外键关联，无法建真实外键；个股数据量级远大于板块（5000+ vs 几十），混表拖累索引与查询；字段语义混杂（个股/板块各有专属死字段）。物理拆表彻底解决，且板块侧零改动
- **风险与对策**：风险是改动面大。对策是共享工具方法（ma_data_loader / ranking_service 等）采用"按 entity_type 内部分发模型类"的最小侵入改法，保持外部签名不变

### ADR-2：旧股票数据不迁移，读路径只读新表

- **选择**：旧表中 entity_type='stock' 的历史数据留在原表，既不删除也不读取；新表靠后续增量采集积累
- **理由**：拆分动作与数据搬移解耦，单次变更风险可控；股票数据可重新采集；读时 union 新旧表会永久增加读路径复杂度，违背拆表初衷
- **风险与对策**：风险是长周期指标（如 240 日均线）有约 1 年的空窗期。对策是接受该约束（PRD 已确认，AC-07 落地），按既有"数据不足"方式呈现，前端零改动

### ADR-3：新表字段裁剪规则

- **选择**：新表去除 `entity_type` 列（恒为 stock）；`stock_strength_scores` 额外去除 `period` 列（已废弃、恒为 'all'）与板块专属字段（`avg_stock_score` / `strong_stock_ratio` / `up_stock_ratio` / `volume_ratio`）；**保留** `percentile` 列与个股专属字段（`ma5_score` 等）
- **理由**：去除无意义字段收敛语义；但 `percentile` 虽在模型层未显式定义（靠 `ranking_service.py:91` 运行时 setattr），DB 实际存在该列且 stocks.py / rankings.py 读取它，缺失会导致运行时报错；个股字段虽当前无写入，照搬避免破坏 schema 完整性，清理留作后续
- **风险与对策**：风险是漏掉 percentile 导致 ranking 写个股排名时炸。对策是 ADR-3 显式列出，新表迁移与模型必须包含 percentile 列；实施阶段用 grep 复核 `percentile` 引用点

### ADR-4：共享工具方法的内部分发策略

- **选择**：`ma_data_loader` / `strength_service_v2._save_strength_score` / `ranking_service` / `strength_history_service` 等 stock/sector 共用方法，保持外部签名（含 entity_type 参数）不变，在方法内部按 entity_type 选择模型类（注：`result_saver` 经核实只更新实体表冗余字段、不写三时序表，不在此列）
- **理由**：最小侵入，调用方零改动；外部签名不变降低 API 层改动；entity_type 参数仍保留作为缓存 key 的天然命名空间
- **风险与对策**：风险是分支遗漏或误伤 sector 分支。对策是每个共享方法改动后必须同时跑 stock 与 sector 测试；sector 测试零回归作为门禁

### ADR-5：写入策略保持现状不统一

- **选择**：行情用 `pg_insert.on_conflict_do_nothing`（collector）/ read-modify-write（data_init）；均线用 read-modify-write + 批量 commit；强度用 read-modify-write + 逐条 commit。新表延续各自既有策略
- **理由**：本需求目标是存储隔离，不是写入性能优化；统一策略会显著扩大改动面、引入新风险，应作为独立优化项
- **演进余地**：后续若发现强度逐条 commit 性能瓶颈，可在新表上单独优化，不影响板块

### ADR-6：alembic 迁移采用手写 op.create_table

- **选择**：迁移脚本手写 `op.create_table` + 单独 `op.create_index`（参照 `2026_06_10_2119-..._add_top10_float_holders_table.py` 范本），不依赖 autogenerate
- **理由**：autogenerate 会夹带既有 DB 与模型历史不同步的噪音（broker_recommend 迁移的 docstring 已记录此问题），手写可精确控制只创建三张新表
- **风险与对策**：风险是手写遗漏字段或索引。对策是以旧三表模型定义为基准逐字段对照，唯一约束命名按新表语义重新命名

### 5.x 待确认问题

无。所有架构决策已确定，下游可直接进入实现计划。

## 6. 运行链路

### 6.1 链路 L1：股票行情采集入库

1. 调度器/手动触发 `init_historical_data_task` / `backfill_by_date_task` / `backfill_by_range_task`
2. task handler 调用 `DataInitService.init_historical_data[_by_date_range]` 或 `DataUpdateService.backfill_by_*`
3. 内部调用 `collector.run_daily_update` → `_update_market_data` 股票分支
4. `pg_insert(StockDailyMarketData).values(stock_id=stock.id, symbol=..., date=..., open/high/low/close/volume/turnover/change/change_percent)`，`on_conflict_do_nothing(constraint='uq_stock_daily_market_data_stock_date')`
5. 分批 commit（batch_size=50）

实现原则：
- `entity_type` 字段不再赋值（新表无此列）；`entity_id` 改名为 `stock_id`（指向 `stocks.id`，不加外键约束，与 top10_float_holders/broker_recommend 风格一致）
- collector 与 data_init 两条写入路径都需切新表（data_init 用 read-modify-write + ORM add，照搬旧逻辑仅替换模型类）

### 6.2 链路 L2：股票均线计算

1. service 直调 `StockMAService.calculate_stock_moving_averages` / `backfill_stock_ma` / `calculate_full_history_ma`
2. 内部 `select(StockMovingAverageData)` 查最新 date 做断点续传
3. 计算各周期（默认 `[5,10,20,30,60]`）均线
4. `select(StockMovingAverageData)` 查重 → 未命中则 `session.add(StockMovingAverageData(stock_id=..., symbol=..., date=..., period='5d', ma_value=..., price_ratio=..., trend=...))`
5. 分批 commit（batch_size=500）

实现原则：
- 均线表 period 列保留（与强度表不同，均线表 period 是真实业务字段）
- read-modify-write 模式照搬，仅替换模型类

### 6.3 链路 L3：股票强度计算与排名

1. API 触发 `StrengthServiceV2.calculate_stock_strength(stock_id, date)` 或 `batch_calculate(entity_type='stock')`
2. `MADataLoader.load_ma_values(entity_type='stock', ...)` 与 `load_current_price(entity_type='stock', ...)` → 内部分发读 `stock_moving_average_data` / `stock_daily_market_data`
3. 计算综合强度 → `_save_strength_score(entity_type='stock', ...)` 内部分发 `select(StockStrengthScore)` 查重 → update 或 `session.add(StockStrengthScore(...))`
4. `calculate_and_update_change_rate(entity_type='stock', ...)` 事后更新 change_rate_1d
5. `RankingService.calculate_rankings` 循环到 entity_type='stock' 时选 `StockStrengthScore` → 内存排序 → setattr `rank` 与 `percentile` → commit

实现原则：
- `_save_strength_score` 写入字段：score / price_position_score / ma_alignment_score / ma_alignment_state / short/medium/long_term_score / strength_grade / current_price / ma5..ma240 / price_above_ma5..240 / change_rate_1d（与旧表写入字段一一对应，不含板块专属字段）
- percentile 列必须存在于新表（ranking_service 运行时 setattr，DB 必须有列）
- ma_data_loader 是共享工具，改动后必须同时验证板块（entity_type='sector'）查询仍走旧表

### 6.4 链路 L4：股票读路径（API 直查）

1. 前端调 `/api/v1/stocks/{stock_id}/strength`、`/api/v1/rankings/v2/stocks`、`/api/v1/strength/...`（stock 分支）
2. handler 内 `select(StockStrengthScore).where(stock_id=..., period-不再-需要)` 或 `select(StockMovingAverageData)`
3. 查不到时 `stocks.py:267-277` 的 fallback 调 `StrengthServiceV2.calculate_stock_strength` 重算
4. 按既有响应 schema（StockStrengthResponse / StrengthRankingResponse 等）序列化返回，`entity_type` 字段硬填 "stock"

实现原则：
- 响应字段名、类型、结构、包裹方式（V2 强度类裸返回专用模型）保持不变
- 前端零依赖 entity_type（已确认 web/src 全量 grep 0 命中），保留仅为响应契约稳定

### 6.5 链路 L5：股票级联删除

1. `DataInitService.init_stocks` 检测到退市/消失股票 → `_cleanup_disappeared_stocks` → `_cleanup_one_market`（带 5% 误删防护）
2. `_cascade_delete_stock_data(stock_ids, symbols)`：`for model in (StockDailyMarketData, StockMovingAverageData, StockStrengthScore): delete(model).where(stock_id.in_(stock_ids))`
3. 继续清理 `SectorStock`（按 stock_code）、`Top10FloatHolder`（按 symbol）、`Stock` 本身

实现原则：
- 三张新表 + SectorStock + Top10FloatHolder + Stock 六元组清理顺序不变
- 防护逻辑（5% 误删阈值）照搬

## 10. 架构结论

本期架构的核心判断：

1. **物理拆表是正确选择**：共用表的软外键、字段语义混杂、量级失衡是结构性问题，物理拆表彻底解决，板块侧零改动风险最低
2. **最小侵入改法是关键**：共享工具方法采用"按 entity_type 内部分发模型类"策略，外部签名不变，调用方零改动，把改动面收敛到工具方法内部
3. **明确接受空窗期换取实施简单度**：旧数据不迁移、读路径不 union，避免永久复杂度，长周期指标空窗靠后续采集自然恢复
4. **关键风险是 percentile 幽灵字段与板块回归**：ADR-3 已显式声明 percentile 必须保留；共享方法改动后 stock/sector 测试同跑作为门禁

演进方向：后续可基于独立的新表做写入性能优化（如强度逐条 commit 改批量）、字段语义清理（个股死字段 ma5_score 等）、为股票补独立 task handler 实现调度对称性。这些都不在本期范围。
