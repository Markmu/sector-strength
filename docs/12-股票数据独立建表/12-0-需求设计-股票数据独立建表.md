# 12-0 需求设计：股票数据独立建表

## 0. 文档说明

**产品核心目标**：为 A 股板块强度分析系统提供准确的板块与个股强度数据支撑。

**本需求定位**：在已有"板块+个股共用时序表"的基础上，将个股数据拆分到独立的股票新存储，实现板块数据与个股数据彻底分开。

**相关文档**：
- 上游决策：本次会话"查看股票历史数据/均线数据是否与板块共用"的拆分确认结论
- 后续文档：`12-1-架构文档-股票数据独立建表.md`（待生成）

## 第一部分：需求分析与确认

### 1.1 项目背景

**产品当前状态**：系统通过采集外部行情数据计算个股与板块的强度得分、均线趋势，支撑个股分析、板块分析、排名等场景。

**存在的问题**：
1. 个股日线行情、均线数据、强度得分三类数据与板块数据共用同一张表，仅靠"数据类别"标记区分
2. 个股数据量级远大于板块（A 股 5000+ 只股票 vs 几十个板块），单表数据膨胀快，查询时需要额外过滤，效率受影响
3. 两类数据的字段含义实际不同：个股有专属的均线得分、动量得分、成交量得分等字段；板块有专属的平均个股强度、强势股占比等字段，混在一张表里导致大量字段对另一类恒为空
4. 两类数据共用一张表，无法保证数据间的关联完整性，只能靠程序代码临时拼接，存在脏数据风险

**本期目标**：让个股的三类时序数据（行情、均线、强度）存入独立的股票数据存储，板块继续使用原存储，两类数据彻底分开。

### 1.2 核心问题定义

| 问题 | 用户/系统损失 |
|---|---|
| 个股与板块数据混表 | 个股数据量级拖累板块查询；任何针对个股的批量操作都可能波及板块数据 |
| 字段语义混杂 | 个股字段和板块字段并存，新增任一类字段都要考虑另一类的兼容性，认知负担高 |
| 软关联无关联完整性约束 | 个股数据完整性只能靠业务代码保证，存在脏数据风险 |
| 表结构演进困难 | 任何对个股数据结构的调整都要兼顾板块，迭代速度受限 |

### 1.3 关键设计决策

| 决策维度 | 最终选择 | 核心理由 | 否决方案 |
|---|---|---|---|
| 拆分范围 | 行情、均线、强度三张表全部拆出股票独立表 | 三类表都存在混表问题，部分拆分会留下半截子工程 | 仅拆行情表（其余两张仍混表，问题未根治） |
| 表命名 | 保留原表名给板块，新建股票新存储 | 板块相关代码量大，保留原名零改动；股票新表加前缀语义清晰 | 原表给股票、板块新建表（板块代码需大量改名，风险高） |
| 历史数据处理 | 仅建新存储不搬数据，旧股票数据留在原存储，新数据写入新存储，读取时只读股票新存储 | 拆分动作与数据搬移解耦，降低单次变更风险；股票数据可重新采集 | 读取时同时合并新旧存储（读取逻辑永久变复杂） |
| 读取策略 | 股票数据的读写都只走股票新存储 | 两类数据彻底分开，路径清晰 | 读取时合并新旧存储（永久复杂度，违背分开存储的初衷） |
| 字段裁剪 | 股票新表去掉"数据类别"标记、不再使用的周期相关字段，以及板块专属字段 | 新表只保留个股语义相关字段 | 完全照搬旧表结构（保留无意义字段） |

### 1.4 产品范围

**本期范围**：
1. 新建三份独立的股票数据存储（行情、均线、强度），包含个股所需的全部字段与数据校验规则
2. 个股数据的所有写入动作切换到新存储（采集入库、初始化、增量更新、补齐）
3. 个股数据的所有读取动作切换到新存储（强度计算、均线计算、排名、历史、分析接口、随个股删除一并清理其相关数据）
4. 板块相关代码与原存储完全不动，继续使用原存储

**明确不做**：
- 旧股票历史数据迁移（接受重新采集积累）
- 长周期指标（如 240 日均线）的空窗期补偿（属于已知约束，靠后续采集自然恢复）
- 对外接口的返回字段与前端界面的任何改动（保持现有约定）
- 缓存命名调整（保留现状以降低风险）
- 暂不重写已废弃的数据访问代码

## 第二部分：用户旅程和用户故事

### 2.1 核心用户旅程

本需求为后端数据架构改造，用户可观察的旅程是"功能正延续 + 性能/稳定性收益"，无新交互流程。核心旅程为数据维护者视角：

```text
数据维护者触发个股数据采集
  → 系统将个股行情/均线/强度存入股票新存储
  → 个股新表只保留个股相关字段，板块专属字段不入新表
  → 个股分析、个股排名、个股强度历史等读取动作从股票新存储读取
  → 板块相关功能继续从原存储读取，行为完全不变
```

异常旅程：
- 采集失败：与改造前行为一致，新存储不写入数据，重试机制不变
- 读取时新存储无数据：表现为相应个股指标为空（与首次上线采集未完成时一致），随采集积累逐步恢复

### 2.2 用户故事

**核心用户故事**：
- 作为数据维护者，我希望个股数据和板块数据存储在各自独立的表中，以便一类数据的批量操作或结构演进不影响另一类
- 作为个股分析功能的使用者，我希望个股的行情、均线、强度数据准确完整，以便分析结论可信

**延伸用户故事**：
- 作为板块分析功能的使用者，我希望本次改造后板块相关功能行为完全不变，以便我的既有使用习惯不受干扰
- 作为后续开发者，我希望个股表只含个股相关字段，以便我理解表结构和新增字段时无需考虑板块兼容性

## 第三部分：UX/UE 设计

本需求无用户可见界面变化，故不绘制线框图。本节定义改造前后用户可观察行为的规则边界。

### 3.1 关键状态

| 状态 | 用户可观察结果 | 用户下一步 |
|---|---|---|
| 个股数据采集进行中 | 个股行情/均线/强度逐步写入股票新存储；前端无变化 | 等待采集完成 |
| 采集完成 | 个股分析、排名、强度历史接口返回新存储数据，行为与改造前一致 | 正常使用 |
| 板块功能使用 | 行为与改造前完全一致 | 正常使用 |

### 3.2 业务规则

- **数据隔离规则**：个股数据只写入和读取股票新存储；板块数据只写入和读取原存储。两类数据互不干扰
- **行为不变规则**：改造后，个股相关功能（个股分析、个股排名、个股强度历史）与板块相关功能（板块分析、板块排名、板块强度历史）的用户可观察行为与改造前一致，不新增、不删除、不改变任何功能
- **空窗期呈现规则**：股票新存储上线初期，部分需要长历史积累的指标（如 240 日均线）会显示为空，这是数据重新采集过程中的正常状态，前端按既有"数据不足"的呈现方式处理，无需新增降级逻辑

## 第四部分：验收标准

- **AC-01：股票数据彻底分开**
  前置：股票新存储已建立，采集任务已运行
  动作：触发个股行情/均线/强度数据采集
  结果：新写入的个股数据全部落入股票新存储，原存储中不再新增个股类型记录

- **AC-02：个股读取动作切换**
  前置：股票新存储已有采集数据
  动作：访问个股分析页、个股排名、个股强度历史接口
  结果：返回数据来源于股票新存储，展示行为与改造前一致

- **AC-03：板块功能零回归**
  前置：原表保留板块数据，板块相关代码未改动
  动作：访问板块分析、板块排名、板块强度历史、板块成分股强势股等全部板块功能
  结果：所有板块功能行为与改造前完全一致，无报错、无数据缺失、无字段变化

- **AC-04：随个股删除清理数据**
  前置：股票新存储已建立，存在个股数据
  动作：触发个股数据清理（如重新初始化个股）
  结果：对应个股的相关数据被正确清理，原存储中板块数据不受影响

- **AC-05：字段语义收敛**
  前置：股票新存储已建立
  动作：审查股票新存储结构
  结果：股票新表不含"数据类别"标记字段、不含板块专属字段（平均个股强度、强势股占比等），仅保留个股语义相关字段

- **AC-06：对外接口约定不变**
  前置：个股相关接口已切换到读股票新存储
  动作：调用个股相关接口并对比改造前后的返回字段与结构
  结果：返回的字段名、类型、结构保持不变，前端无需配合改动

- **AC-07：长周期指标空窗期呈现**
  前置：股票新存储上线初期，部分个股数据尚未采集满
  动作：访问依赖长历史积累的个股指标（如 240 日均线）
  结果：相应指标呈现为空或"数据不足"，呈现方式与改造前首次上线未采集完成时一致，前端无需新增降级逻辑
