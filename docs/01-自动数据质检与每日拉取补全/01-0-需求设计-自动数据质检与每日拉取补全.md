# 01-0 需求设计：自动数据质检与每日拉取补全

## 0. 文档说明

**产品核心目标**：为投资者提供基于多周期均线的板块/个股强度指标，辅助市场研判决策。

**本需求定位**：已有调度框架和异步任务系统的基础上，补全数据质检检测逻辑和每日数据采集的持久化流程，使"每日自动更新 → 质检 → 异常告警"链路真正跑通。

**相关文档**：
- 无前置文档（本期为首个正式需求文档）

## 第一部分：需求分析与确认

### 1.1 项目背景

产品当前状态：定时任务调度器和异步任务执行器已搭建完成，14 种任务类型可正常注册和执行，板块/股票初始化、历史数据拉取、均线计算、强度计算等服务层已实现并通过任务系统工作。

存在的问题：

1. **数据质检永远无问题**：质检定时任务每 5 分钟运行一次，但缺失检测逻辑直接返回 0，无法发现数据缺失。且质检不回溯历史缺口，即使某日更新失败跳过，后续不会自动补齐
2. **每日数据更新不落库**：每日定时任务会调用数据源获取板块列表和股票列表，但获取后只计数不写入数据库，行情数据仅处理前 10 只股票且同样不保存
3. **交易日判断过于简单**：仅排除周末和元旦，中国 A 股市场的法定节假日调休均未纳入，导致非交易日白白执行更新、调休日反而跳过
4. **数据库健康检查形同虚设**：健康检查端点不验证实际连接，即使数据库宕机也返回"健康"
5. **告警只记日志不可见**：发现数据质量问题后仅写日志，管理员无法及时感知

本期目标：让"交易日判断 → 数据拉取落库 → 质检发现缺失 → 自动补齐 → 告警通知管理员"这条自动化链路完整闭环。

### 1.2 核心问题定义

| 问题 | 管理员损失 |
|------|-----------|
| 数据质检不检测，永远报告无问题 | 数据缺失或异常长时间未被发现，导致前端展示的强度指标基于不完整数据，误导投资判断 |
| 每日拉取不落库，等于没拉 | 依赖手动触发任务才能更新数据，自动化名存实亡，管理员需每天盯盘后手动操作 |
| 交易日判断不区分节假日调休 | 非交易日白白消耗数据源配额和系统资源；调休工作日却跳过更新，错过当天数据 |
| 健康检查不查库 | 数据库故障时运维告警链路断裂，问题暴露延迟 |
| 告警只写日志，无结构化记录 | 管理员必须主动翻日志才能发现问题，失去"自动化监控"的意义（本期不引入告警系统，留待后续独立需求） |

### 1.3 关键设计决策

| 决策维度 | 最终选择 | 核心理由 | 否决方案 |
|---------|---------|---------|---------|
| 每日更新流程 | 复用现有数据初始化和更新服务，由采集协调器编排调用 | 这些服务已通过异步任务系统验证可用，重新实现是重复劳动且引入新 bug | 在采集协调器中重新实现数据获取和保存逻辑 |
| 交易日历 | 调用数据源的交易日期接口获取真实交易日历 | 数据源本身提供权威的 A 股交易日历，无需自行维护 | 硬编码节假日规则（维护成本高且容易遗漏） |
| 告警通道 | 本期不引入告警系统，质检发现问题自动补齐，补齐失败时通过日志记录 | 检测+补齐是核心价值，告警通知需要额外基础设施，独立迭代 | 直接集成告警记录或通知系统 |
| 质检频率 | 改为每小时一次 | 现有调度每 5 分钟过于频繁，数据完整性无需如此高频检查 | 降低频率（遗漏检测窗口）/ 保持 5 分钟（增加数据库负载） |
| 质检范围 | 检查数据完整性并自动补齐：先检查最新交易日数据完整性，发现缺失或日期缺口则自动补齐最新日期+1至当日所有交易日数据 | 数据完整性和连续性是最关键的质量指标，异常价格等深度检测留待后续 | 全面数据质量审计（本期过重） |

### 1.4 产品范围

**本期范围**：

1. 实现数据完整性检测与自动补齐逻辑：检查最新交易日数据完整性，发现缺失或日期缺口则自动补齐最新日期+1至当日所有交易日数据
2. 补全每日数据更新的落库流程：板块数据同步、股票数据同步、行情数据采集与保存
3. 集成真实交易日历判断
4. 数据库健康检查端点验证实际连接
5. 质检支持手动触发

**明确不做**：

- 告警系统（结构化告警记录、告警通知）— 留待后续独立需求
- 外部告警通道（邮件、短信、即时消息）的集成 — 留待后续独立需求
- 历史数据全量一致性审计 — 本期只检查最新交易日
- 前端管理界面改造 — 现有管理后台 API 返回真实数据即可
- 数据源故障时的自动降级策略（如切换备用数据源）
- 交易日历的离线缓存和手动维护机制

## 第二部分：用户旅程和用户故事

### 2.1 核心用户旅程

目标用户：系统管理员（负责监控和维护数据管道正常运行）

**主旅程：自动化数据更新与质检**

```
1. 每个交易日收盘后（约 15:30），系统自动判断今日是否为交易日
   → 是交易日：继续下一步
   → 非交易日（节假日/周末）：跳过本次更新，记录跳过原因

2. 系统自动拉取最新板块列表，新增板块写入数据库，已有板块更新信息
   → 板块数据更新完成

3. 系统自动拉取最新股票列表，新增股票写入数据库，已有股票更新信息
   → 股票数据更新完成

4. 系统按板块逐个拉取当日行情数据，写入行情数据表
   → 行情数据更新完成

5. 系统自动触发板块分类、均线计算、强度计算等后续计算流程
   → 计算完成

6. 质检任务（每小时）检查数据完整性，发现缺失或日期缺口则自动补齐最新日期+1至当日所有交易日数据（也支持手动触发）
   → 发现缺失并补齐：自动拉取缺失交易日数据并触发计算
   → 一切正常：无额外操作
```

**异常旅程：数据源不可用**

```
步骤 2-4 中，若数据源请求失败：
  → 系统记录失败原因，标记本次更新为失败
  → 管理员通过管理 API 查看失败记录，手动重新触发更新
  → 质检任务在下次运行时发现最新数据缺失，记录告警
```

**异常旅程：质检发现缺失**

```
步骤 6 中，若检测到缺失数据或日期缺口：
  → 系统自动补齐缺失交易日的行情数据
  → 补齐失败（如数据源部分不可用）：记录日志，下次质检继续尝试补齐
  → 管理员也可随时手动触发质检，立即获取数据完整性报告
```

### 2.2 用户故事

**核心用户故事：**

- US-01：作为管理员，我希望每个交易日收盘后系统自动完成数据更新，以便我不需要每天手动触发任务
- US-02：作为管理员，我希望系统能自动检测行情数据的缺失并自动补齐，以便数据保持完整连续
- US-03：作为管理员，我希望节假日和调休日能被正确识别，以便不会在非交易日白白运行更新，也不会在调休工作日漏掉更新
- US-04：作为管理员，我希望数据库健康检查能反映真实状态，以便运维监控系统能准确报警

**延伸用户故事：**

- US-05：作为管理员，我希望质检能自动补齐缺失数据，以便数据保持完整连续而无需我手动干预

### 3.2 关键状态

| 状态 | 表现 | 用户下一步 |
|------|------|-----------|
| 每日更新成功 | 任务日志记录更新统计（更新板块数、股票数、行情条数、计算数） | 无需操作，等待下次自动更新 |
| 每日更新失败 | 任务日志记录失败原因 | 通过管理 API 重新触发更新任务 |
| 质检发现缺失 | 自动补齐缺失交易日数据，补齐失败时记录日志 | 查看日志，手动触发补齐 |
| 质检正常 | 质检报告标记"正常" | 无需操作 |
| 非交易日跳过 | 任务日志记录跳过原因（具体节假日名称或周末） | 无需操作 |
| 数据库连接异常 | 健康检查返回不健康状态和错误信息 | 检查数据库服务状态 |

### 3.3 业务规则

**交易日判断规则**：
- 交易日历从数据源实时获取，不依赖本地硬编码
- 当日非交易日时，每日更新任务跳过执行，日志中记录具体原因（周末 / 节假日名称）

**数据更新规则**：
- 板块数据：拉取后与已有记录对比，新增则插入，已有则更新名称等字段
- 股票数据：同板块数据的对比逻辑
- 行情数据：仅拉取最新交易日数据，已有记录则跳过
- 整个更新流程按板块 → 股票 → 行情 → 计算的顺序依次执行，前一步失败则中止后续步骤

**数据质检规则**：
- 缺失检测：对比已注册股票数量与最新交易日有行情数据的数量，差值即为缺失数
- 日期缺口检测：查询数据库中最新数据日期，若 latest_date+1 至当日之间存在交易日无数据，视为日期缺口
- 自动补齐：发现缺失或日期缺口时，自动拉取对应交易日的板块和个股行情数据，写入数据库并触发计算
- 补齐范围严格限定为 latest_date+1 至当日，不回溯更早的历史数据
- 质检结果作为结构化数据保存，供管理 API 查询
- 支持通过 API 手动触发质检

## 第四部分：验收标准

- AC-01：交易日自动更新完整执行
  前置：当日为交易日，数据库中有板块和股票记录
  动作：等待每日定时任务触发（或手动触发每日更新）
  结果：板块数据同步到最新列表，股票数据同步到最新列表，最新交易日行情数据已入库，后续计算任务已完成；管理 API 可查到本次更新的统计记录

- AC-02：非交易日自动跳过
  前置：当日为周末或法定节假日
  动作：等待每日定时任务触发
  结果：日志中记录跳过原因，不执行任何数据拉取操作

- AC-03：调休工作日正常执行
  前置：当日为周末调休为工作日
  动作：等待每日定时任务触发
  结果：与 AC-01 相同，正常执行数据更新全流程

- AC-04：数据质检发现缺失并自动补齐
  前置：数据库中最新数据日期为 T-2，T-1 和 T 为交易日且数据缺失
  动作：等待质检任务执行（或手动触发质检）
  结果：质检自动拉取 T-1 和 T 的行情数据并入库，触发计算；质检报告包含补齐结果

- AC-05：数据库健康检查真实反映连接状态
  前置：数据库服务正常运行
  动作：调用健康检查接口
  结果：返回健康状态
  补充验证：停止数据库服务后调用同一接口，返回不健康状态和错误信息

- AC-06：数据源失败后可恢复
  前置：每日更新任务因数据源不可用而失败
  动作：管理员通过管理 API 查看失败记录，手动重新触发更新任务
  结果：更新任务重新执行并完成，数据正常入库

- AC-07：手动触发质检
  前置：系统正常运行
  动作：通过管理 API 手动触发质检
  结果：立即返回数据完整性报告，包含最新交易日的数据缺失情况
